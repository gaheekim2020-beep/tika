# Feature Specification: 티켓 삭제 API

**Feature Branch**: `[006-delete-ticket-api]`

**Created**: 2026-09-30

**Status**: Draft

**Input**: User description: "docs/API_SPEC.md의 6. `DELETE /api/tickets/:id` — 티켓 삭제 API를 구현하기 위한 명세를 작성한다. API_SPEC.md, DATA_MODEL.md, TEST_CASES.md의 관련 내용을 기준으로 한다."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 더 이상 필요 없는 할 일 삭제하기 (Priority: P1)

사용자는 잘못 만들었거나 더 이상 필요 없어진 할 일을 보드에서 완전히 없애고 싶어한다. 삭제를 요청하면 그 할 일이 즉시 사라지고, 이후 보드를 다시 불러오거나 그 할 일을 직접 조회해도 다시 나타나지 않길 기대한다.

**Why this priority**: 생성(001), 목록(002), 상세 조회(003), 수정(004), 완료(005)까지 구현된 지금, 삭제는 US-008(할 일 삭제)의 핵심이며 할 일의 전체 생명주기(생성 → 관리 → 제거)를 완성하는 기능이다. 삭제가 없으면 잘못 만든 할 일을 치울 방법이 없다.

**Independent Test**: 할 일을 하나 만든 뒤 삭제를 요청했을 때 성공(본문 없음) 응답을 받고, 이후 같은 식별자로 조회하면 "찾을 수 없음"이 반환되는지 확인하는 것만으로 독립적으로 테스트 가능하다.

**Acceptance Scenarios**:

1. **Given** 할 일이 존재하는 상태에서, **When** 사용자가 그 할 일의 삭제를 요청하면, **Then** 시스템은 본문 없는 성공 응답을 반환하고 그 할 일은 더 이상 존재하지 않는다.
2. **Given** 삭제에 성공한 직후, **When** 같은 식별자로 상세 조회를 요청하면, **Then** "찾을 수 없음" 응답을 받는다.
3. **Given** 삭제에 성공한 직후, **When** 보드 목록을 조회하면, **Then** 삭제된 할 일은 어느 칼럼에도 포함되지 않는다.
4. **Given** 백로그·할 일·진행 중·완료 어느 상태의 할 일이든, **When** 사용자가 삭제를 요청하면, **Then** 상태와 관계없이 동일하게 삭제된다.

---

### User Story 2 - 삭제는 되돌릴 수 없는 완전 삭제 (Priority: P2)

사용자는 삭제된 할 일이 "숨김" 처리가 아니라 저장소에서 완전히 제거되기를 기대한다. 삭제 후에는 어떤 조회 경로로도 그 할 일의 흔적이 남지 않아야 한다.

**Why this priority**: 삭제 동작 자체(P1)가 먼저이고, 그 삭제가 "완전 삭제(Hard Delete)"라는 성질은 데이터 정합성에 관한 보증이다. 기본 삭제 없이는 의미가 없어 그다음 우선순위다.

**Independent Test**: 할 일을 삭제한 직후 저장된 데이터를 직접 확인했을 때 해당 행이 남아 있지 않고, 삭제 표시(soft-delete) 같은 별도 플래그도 존재하지 않는지 확인하는 것으로 독립적으로 테스트 가능하다.

**Acceptance Scenarios**:

1. **Given** 할 일을 삭제한 직후, **When** 저장된 데이터를 직접 확인하면, **Then** 해당 식별자의 행이 존재하지 않는다.
2. **Given** 여러 할 일이 있는 상태에서 그중 하나를 삭제하면, **When** 나머지 할 일을 조회하면, **Then** 나머지 할 일의 내용과 순서값은 삭제 전과 동일하다.

---

### User Story 3 - 존재하지 않는 항목·잘못된 식별자 삭제 시도 처리 (Priority: P3)

사용자(또는 클라이언트 화면)는 이미 삭제되었거나 존재한 적 없는 할 일, 혹은 형식이 잘못된 식별자로 삭제를 시도했을 때 명확한 실패 안내를 받고 싶어한다.

**Why this priority**: 드물게 발생하는 방어적 시나리오(오래 열려 있던 화면, 두 화면에서의 중복 삭제, 잘못된 링크 등)이며, 정상 삭제가 먼저 갖춰져야 의미가 있다.

**Independent Test**: 존재하지 않는 식별자, 이미 삭제한 식별자, 숫자가 아니거나 0/음수인 식별자로 각각 삭제를 요청했을 때, "찾을 수 없음"과 "유효하지 않은 식별자" 응답이 각각 오는지 확인하는 것으로 독립적으로 테스트 가능하다.

**Acceptance Scenarios**:

1. **Given** 어떤 할 일도 존재하지 않는 식별자가 주어진 상태에서, **When** 사용자가 삭제를 요청하면, **Then** 시스템은 "존재하지 않는 할 일"임을 명확히 안내하고 어떤 데이터도 변경하지 않는다.
2. **Given** 방금 삭제한 할 일의 식별자로, **When** 사용자가 다시 삭제를 요청하면, **Then** 성공이 아니라 "찾을 수 없음"으로 안내한다.
3. **Given** 식별자가 숫자 형식이 아니거나 0 이하인 상태에서, **When** 사용자가 삭제를 요청하면, **Then** 시스템은 식별자가 유효하지 않다고 안내하고 삭제를 시도하지 않는다.

---

### Edge Cases

- 이미 삭제된 할 일을 다시 삭제하면 어떻게 되는가? → 성공으로 처리하지 않고 "찾을 수 없음"으로 안내한다(완료 처리(005)와 달리 삭제 API는 재시도를 성공으로 취급하지 않는다. `docs/TEST_CASES.md` TC-API-006-05).
- 삭제 요청에 본문(body)을 함께 보내면 어떻게 되는가? → 이 기능은 본문을 사용하지 않으므로 본문의 내용은 무시되고, 본문이 없는 요청과 동일하게 처리된다.
- 완료(DONE) 상태로 24시간이 지나 보드에서 보이지 않는 할 일도 삭제할 수 있는가? → 보드 노출 여부와 무관하게 저장소에 남아 있는 한 식별자로 삭제할 수 있다.
- 삭제된 할 일이 차지하던 칼럼 내 순서값은 어떻게 되는가? → 나머지 할 일의 순서값은 변경하지 않는다. 순서값은 오름차순 정렬 기준일 뿐 연속일 필요가 없어, 중간이 비어도 표시 순서에 영향이 없다.
- 두 화면에서 같은 할 일을 동시에 삭제하면 어떻게 되는가? → 먼저 처리된 요청만 성공하고, 뒤에 도착한 요청은 이미 없는 할 일이므로 "찾을 수 없음"으로 안내된다. 최종 상태는 어느 경우에도 "삭제됨"으로 동일하다.
- 데이터베이스 연결 실패 등 예상치 못한 오류가 발생하면 어떻게 되는가? → 사용자에게 삭제하지 못했다는 일반적인 오류 안내가 표시되고 할 일은 삭제되지 않은 채 그대로 남는다.
- 삭제 전 확인("정말 삭제하시겠습니까?")은 누가 담당하는가? → 확인 절차는 화면(프론트엔드)의 책임이며(TC-COMP-008), 서버는 요청을 받으면 곧바로 삭제한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 사용자가 식별자로 지정한 할 일 하나를 삭제할 수 있게 해야 한다. 삭제는 백로그, 할 일, 진행 중, 완료 어느 상태의 할 일에서도 가능해야 한다.
- **FR-002**: 시스템은 삭제에 성공하면 본문 없는 성공 응답을 반환해야 한다.
- **FR-003**: 시스템은 삭제를 저장소에서 행을 완전히 제거하는 방식(Hard Delete)으로 처리해야 하며, 삭제 표시 플래그 등으로 흔적을 남기지 않아야 한다.
- **FR-004**: 시스템은 삭제된 할 일이 이후 상세 조회에서 "찾을 수 없음"으로 응답되고, 보드 목록 조회 결과에 포함되지 않게 해야 한다.
- **FR-005**: 시스템은 삭제 시 다른 할 일의 내용과 순서값을 변경하지 않아야 한다.
- **FR-006**: 시스템은 요청 본문을 사용하지 않아야 한다. 본문이 없어도 정상 동작하며, 본문이 있더라도 그 내용은 처리 결과에 영향을 주지 않는다.
- **FR-007**: 시스템은 존재하지 않거나 이미 삭제된 식별자로 삭제를 요청받으면, 성공으로 처리하지 않고 명확한 "찾을 수 없음" 응답을 반환해야 하며 어떤 데이터도 변경하지 않아야 한다. 이때 안내 문구는 이미 구현된 003·004·005와 동일하게 "존재하지 않거나 삭제된 티켓입니다"로 통일한다.
- **FR-008**: 시스템은 식별자가 숫자가 아니거나 양의 정수가 아니면, 삭제를 시도하지 않고 "유효하지 않은 식별자" 응답을 반환해야 한다.
- **FR-009**: 시스템은 예기치 못한 내부 오류로 삭제가 실패한 경우, 사용자에게 삭제하지 못했다는 일반적인 오류를 안내하고 할 일을 삭제하지 않은 채로 유지해야 한다.

### Key Entities

- **할 일 항목(Ticket)**: `001-create-ticket-api`~`005-complete-ticket-api`에서 정의된 것과 동일한 엔티티. 이번 기능은 새 필드를 추가하지 않으며, 지정된 항목 하나를 저장소에서 완전히 제거하는 것이 전부다. 삭제 후에는 식별자를 포함해 어떤 속성도 남지 않는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 사용자는 백로그·할 일·진행 중·완료 어느 상태의 할 일이든 한 번의 요청으로 삭제할 수 있고, 성공한 모든 요청에서 본문 없는 성공 응답을 받는다.
- **SC-002**: 삭제에 성공한 모든 요청 이후, 같은 식별자로 조회하면 100% "찾을 수 없음"이 반환되고 보드 목록에도 100% 나타나지 않는다.
- **SC-003**: 삭제 직후 저장된 데이터에는 해당 할 일의 흔적이 100% 남아 있지 않다.
- **SC-004**: 삭제 후 나머지 할 일의 내용과 순서값은 100% 삭제 전과 동일하다.
- **SC-005**: 존재하지 않거나 이미 삭제된 식별자 또는 형식이 잘못된 식별자로 삭제를 요청한 경우 100% 각각 "찾을 수 없음"/"유효하지 않은 식별자" 응답을 받으며, 성공이나 서버 오류로 오인되지 않는다.

## Assumptions

- 이번 기능은 `001`~`005`에서 정의된 할 일 항목(Ticket) 데이터 구조를 그대로 사용하며 새로운 데이터 항목을 추가하지 않는다.
- 삭제는 `docs/API_SPEC.md` 6번과 `docs/REQUIREMENTS.md`(FR-006)에 따라 Hard Delete이며, 휴지통·복구 기능은 제공하지 않는다.
- 이미 삭제된 할 일을 다시 삭제하는 요청은 `docs/TEST_CASES.md` TC-API-006-05에 따라 "찾을 수 없음"으로 처리한다(완료 처리의 "이미 완료 시 성공" 규칙과 다르다).
- 삭제로 생긴 칼럼 내 순서값의 빈 자리는 재정렬하지 않는다(`docs/DATA_MODEL.md`의 순서값 규칙은 오름차순 정렬만 요구하고 연속성을 요구하지 않는다).
- 삭제 확인 다이얼로그, 삭제 실패 토스트, 삭제 후 보드 갱신 등 화면(프론트엔드) 동작은 `TC-COMP-008`에서 다루며 이번 기능의 범위 밖이다. 이 기능은 서버가 제공하는 삭제 동작만 정의한다.
- 다건 삭제(일괄 삭제), 완료 후 일정 기간 경과 시 자동 삭제는 이번 기능의 범위 밖이다.
- MVP 단계에서는 별도의 로그인/인증 없이 단일 사용자가 사용하는 것을 전제로 한다 (`001-create-ticket-api`와 동일).
