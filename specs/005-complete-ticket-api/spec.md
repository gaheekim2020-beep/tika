# Feature Specification: 티켓 완료 처리 API

**Feature Branch**: `[005-complete-ticket-api]`

**Created**: 2026-09-29

**Status**: Draft

**Input**: User description: "docs/API_SPEC.md의 5번 항목 `PATCH /api/tickets/:id/complete` — 티켓 완료 처리 API를 구현하기 위한 명세를 작성한다. API_SPEC.md, DATA_MODEL.md, TEST_CASES.md의 관련 내용을 기준으로 한다."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 할 일을 완료 처리하기 (Priority: P1)

사용자는 진행 중이거나 예정된 할 일을 끝냈을 때, 그 할 일을 "완료" 상태로 바꾸고 싶어한다. 완료를 누르는 즉시 할 일이 완료 상태가 되고, 언제 완료했는지 기록되며, 최종 수정 시각도 함께 갱신되길 기대한다.

**Why this priority**: 생성(001), 목록(002), 상세 조회(003), 수정(004)까지 구현된 지금, 완료 처리는 US-006(할 일 완료 처리)의 핵심이자 칸반 보드의 목적(할 일을 끝내고 정리하기)을 달성하는 기능이다. 완료 처리가 없으면 할 일이 영원히 남아 보드가 계속 쌓이기만 한다.

**Independent Test**: "할 일(TODO)" 상태의 할 일을 하나 만든 뒤 완료 처리를 요청했을 때, 상태가 "완료"로 바뀌고 완료 시각이 현재 시각으로 기록되며 최종 수정 시각이 갱신되고 지연 여부가 "지연 아님"으로 반환되는지 확인하는 것만으로 독립적으로 테스트 가능하다.

**Acceptance Scenarios**:

1. **Given** "할 일(TODO)" 상태의 할 일이 존재하는 상태에서, **When** 사용자가 완료 처리를 요청하면, **Then** 상태가 "완료(DONE)"로 바뀌고, 완료 시각이 현재 시각으로 기록되며, 최종 수정 시각이 갱신되고, 지연 여부는 "지연 아님"인 할 일이 반환된다.
2. **Given** "진행 중(IN_PROGRESS)" 상태의 할 일이 존재하는 상태에서, **When** 사용자가 완료 처리를 요청하면, **Then** 상태가 "완료(DONE)"로 바뀌고 완료 시각이 현재 시각으로 기록된 할 일이 반환된다.
3. **Given** "백로그(BACKLOG)" 상태의 할 일이 존재하는 상태에서, **When** 사용자가 완료 처리를 요청하면, **Then** 다른 상태와 동일하게 "완료(DONE)"로 바뀐 할 일이 반환된다.
4. **Given** 제목·설명·우선순위·시작예정일·종료예정일이 채워진 할 일이 존재하는 상태에서, **When** 사용자가 완료 처리를 요청하면, **Then** 상태, 완료 시각, 순서, 최종 수정 시각을 제외한 나머지 항목은 기존 값 그대로 유지된다.

---

### User Story 2 - 완료된 할 일이 완료 칼럼 맨 위에 배치되기 (Priority: P2)

사용자는 방금 완료한 할 일이 완료(Done) 칼럼에서 가장 위에 보이길 기대한다. 그래야 "방금 무엇을 끝냈는지"를 바로 확인할 수 있다. 완료 칼럼이 비어 있든 이미 다른 완료 항목이 있든 동일하게 동작해야 한다.

**Why this priority**: 상태를 완료로 바꾸는 것(P1)이 핵심이지만, 완료 칼럼 안에서의 위치 규칙이 없으면 새로 완료한 항목이 임의의 위치에 끼어들어 보드가 일관성 없이 보인다. 다만 P1 없이는 의미가 없으므로 그다음 우선순위다.

**Independent Test**: 완료 칼럼이 비어 있는 상태와, 이미 완료된 할 일이 있는 상태에서 각각 다른 할 일을 완료 처리했을 때, 비어 있으면 기준 시작 순서값(1024)이, 이미 있으면 기존 최솟값보다 작은(더 위에 오는) 순서값이 부여되는지 확인하는 것으로 독립적으로 테스트 가능하다.

**Acceptance Scenarios**:

1. **Given** 완료 칼럼에 할 일이 하나도 없는 상태에서, **When** 사용자가 어떤 할 일을 완료 처리하면, **Then** 그 할 일의 순서값은 1024가 된다.
2. **Given** 완료 칼럼에 순서값 최솟값이 1024인 할 일이 이미 존재하는 상태에서, **When** 사용자가 다른 할 일을 완료 처리하면, **Then** 새로 완료된 할 일의 순서값은 1024 - 1024 = 0으로, 기존 완료 항목들보다 작아 칼럼 맨 위에 배치된다.
3. **Given** 종료예정일이 이미 지난 미완료 할 일이 존재하는 상태에서, **When** 사용자가 그 할 일을 완료 처리하면, **Then** 완료된 할 일은 상태가 "완료"이므로 지연 여부가 "지연 아님"으로 반환된다(완료 상태가 우선 적용된다).

---

### User Story 3 - 존재하지 않는 항목·잘못된 식별자 완료 시도 처리 (Priority: P3)

사용자(또는 클라이언트 화면)는 삭제되었거나 존재한 적 없는 할 일, 혹은 형식이 잘못된 식별자로 완료를 시도했을 때 명확한 실패 안내를 받고 싶어한다.

**Why this priority**: 드물게 발생하는 방어적 시나리오(오래 열려 있던 화면, 잘못된 링크 등)이며, 정상 완료 처리와 배치 규칙이 먼저 갖춰져야 의미가 있다.

**Independent Test**: 존재하지 않는 식별자와 숫자가 아니거나 0/음수인 식별자로 각각 완료를 요청했을 때, "찾을 수 없음"과 "유효하지 않은 식별자" 응답이 각각 오는지 확인하는 것으로 독립적으로 테스트 가능하다.

**Acceptance Scenarios**:

1. **Given** 어떤 할 일도 존재하지 않는 식별자가 주어진 상태에서, **When** 사용자가 완료 처리를 요청하면, **Then** 시스템은 "존재하지 않거나 삭제된 할 일"임을 명확히 안내하고 어떤 데이터도 변경하지 않는다.
2. **Given** 식별자가 숫자 형식이 아니거나 0 이하인 상태에서, **When** 사용자가 완료 처리를 요청하면, **Then** 시스템은 식별자가 유효하지 않다고 안내하고 완료 처리를 시도하지 않는다.

---

### Edge Cases

- 이미 완료(DONE) 상태인 할 일에 다시 완료 처리를 요청하면 어떻게 되는가? → 오류로 거절하지 않고 성공으로 처리하며, 완료 시각·순서·최종 수정 시각은 바뀌지 않은 현재 할 일을 그대로 반환한다(중복 클릭·재시도에도 안전).
- 완료 처리 요청에 본문(body)을 함께 보내면 어떻게 되는가? → 이 기능은 본문을 사용하지 않으므로 본문의 내용은 무시되고, 본문이 없는 요청과 동일하게 처리된다.
- 요청에 상태·순서 등 다른 값을 담아 보내면 어떻게 되는가? → 본문이 무시되므로 완료 처리 결과(상태=완료, 순서=완료 칼럼 맨 위)에는 영향을 주지 않는다.
- 시작 시각(startedAt)은 어떻게 되는가? → 완료 처리는 시작 시각을 건드리지 않는다. 시작 시각은 상태/순서 변경 기능(FR-007)에서만 갱신된다.
- 24시간이 지나면 완료된 할 일은 어떻게 되는가? → 삭제되거나 상태가 바뀌지 않는다. 다만 보드(목록 조회)의 완료 칼럼에서 완료 시각 기준 24시간이 지나면 보이지 않을 뿐이며, 단건 조회로는 계속 확인할 수 있다. 이 규칙은 이번 기능이 아니라 목록 조회 기능이 적용한다.
- 완료된 할 일을 다른 칼럼으로 되돌릴 때 완료 시각은 어떻게 되는가? → 되돌리기와 완료 시각 초기화는 상태/순서 변경 기능(FR-007)이 담당하며 이번 기능의 범위 밖이다. 되돌린 뒤 다시 완료 처리하면 완료 시각은 그때의 새로운 현재 시각으로 기록된다.
- 데이터베이스 연결 실패 등 예상치 못한 오류가 발생하면 어떻게 되는가? → 사용자에게 완료 처리하지 못했다는 일반적인 오류 안내가 표시되고 할 일은 변경되지 않는다.
- 두 화면에서 같은 할 일을 동시에 완료 처리하면 어떻게 되는가? → 어느 쪽이 먼저 처리되든 최종적으로 할 일은 하나의 완료 상태이며, 뒤에 도착한 요청은 이미 완료된 할 일로 취급되어 성공으로 처리된다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 사용자가 식별자로 지정한 할 일 하나를 완료(DONE) 상태로 바꿀 수 있게 해야 한다. 완료 처리는 백로그, 할 일, 진행 중 어느 상태의 할 일에서도 가능해야 한다.
- **FR-002**: 시스템은 완료 처리 시 그 할 일의 완료 시각을 현재 시각으로 기록해야 한다.
- **FR-003**: 시스템은 완료 처리 시 그 할 일을 완료 칼럼의 맨 위에 배치해야 한다. 완료 칼럼에 이미 할 일이 있으면 기존 순서값의 최솟값보다 1024 작은 값을, 완료 칼럼에 할 일이 없으면 1024를 순서값으로 부여한다.
- **FR-004**: 시스템은 완료 처리가 성공할 때마다 최종 수정 시각을 현재 시각으로 갱신해야 한다.
- **FR-005**: 시스템은 완료 처리 결과를 반환할 때 지연(기한 초과) 여부를 항상 "지연 아님"으로 포함해야 한다. 종료예정일이 이미 지난 할 일이라도 완료 상태가 우선 적용된다.
- **FR-006**: 시스템은 완료 처리 시 상태, 완료 시각, 순서, 최종 수정 시각 외의 항목(제목, 설명, 우선순위, 시작예정일, 종료예정일, 시작 시각, 생성 시각)을 변경하지 않아야 한다.
- **FR-007**: 시스템은 요청 본문을 사용하지 않아야 한다. 본문이 없어도 정상 동작하며, 본문이 있더라도 그 내용은 처리 결과에 영향을 주지 않는다.
- **FR-008**: 시스템은 이미 완료(DONE) 상태인 할 일에 대한 완료 요청을 오류로 거절하지 않고 성공으로 처리해야 하며, 이때 완료 시각·순서·최종 수정 시각은 변경하지 않고 현재 할 일을 반환해야 한다.
- **FR-009**: 시스템은 존재하지 않거나 삭제된 식별자로 완료를 요청받으면, 명확한 "찾을 수 없음" 응답을 반환하고 어떤 데이터도 변경하지 않아야 한다.
- **FR-010**: 시스템은 식별자가 숫자가 아니거나 양의 정수가 아니면, 완료 처리를 시도하지 않고 "유효하지 않은 식별자" 응답을 반환해야 한다.
- **FR-011**: 시스템은 예기치 못한 내부 오류로 완료 처리가 실패한 경우, 사용자에게 완료 처리하지 못했다는 일반적인 오류를 안내하고 할 일을 변경하지 않아야 한다.
- **FR-012**: 시스템은 이 기능으로 완료 상태에서 다른 상태로 되돌리는 처리(완료 시각 초기화 포함)를 하지 않아야 한다. 완료 진입만 처리한다.

### Key Entities

- **할 일 항목(Ticket)**: `001-create-ticket-api`, `002-list-tickets-api`, `003-get-ticket-detail`, `004-update-ticket-api`에서 정의된 것과 동일한 엔티티. 이번 기능은 새 필드를 추가하지 않고, 기존 항목 중 상태·완료 시각·순서·최종 수정 시각만 변경한다. 지연 여부는 조회 시점에 계산되는 파생 값으로, 완료 상태에서는 항상 "지연 아님"이다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 사용자는 백로그·할 일·진행 중 어느 상태의 할 일이든 한 번의 요청으로 완료 처리할 수 있고, 성공한 모든 요청에서 상태가 "완료"이며 완료 시각이 기록되어 반환된다.
- **SC-002**: 완료 처리에 성공한 모든 요청에서 최종 수정 시각이 갱신되고 지연 여부는 100% "지연 아님"으로 반환된다(종료예정일이 지난 할 일 포함).
- **SC-003**: 완료 칼럼이 비어 있을 때 완료된 할 일의 순서값은 100% 1024이고, 이미 완료된 할 일이 있을 때는 100% 기존 최솟값보다 작아 칼럼 맨 위에 배치된다.
- **SC-004**: 완료 처리 후에도 제목·설명·우선순위·시작예정일·종료예정일·시작 시각·생성 시각은 100% 이전과 동일하다.
- **SC-005**: 존재하지 않는 식별자 또는 형식이 잘못된 식별자로 완료를 요청한 경우 100% 각각 "찾을 수 없음"/"유효하지 않은 식별자" 응답을 받으며, 빈 성공 응답이나 서버 오류로 오인되지 않는다.
- **SC-006**: 이미 완료된 할 일에 완료를 반복 요청해도 100% 오류 없이 성공하고, 완료 시각과 순서는 처음 완료 처리된 값 그대로 유지된다.

## Assumptions

- 이번 기능은 `001`~`004`에서 정의된 할 일 항목(Ticket) 데이터 구조를 그대로 사용하며 새로운 데이터 항목을 추가하지 않는다.
- **완료 요청이 이미 완료된 할 일에 다시 올 때의 동작(확정)**: `docs/API_SPEC.md`, `docs/DATA_MODEL.md`, `docs/TEST_CASES.md`에는 이 경우의 처리가 정의되어 있지 않아, 중복 클릭·재시도에도 완료 시각과 순서가 흔들리지 않도록 "성공으로 처리하되 값은 바꾸지 않는다"로 확정했다(사용자 결정). 이 동작은 관련 문서(API_SPEC.md 처리 규칙, TEST_CASES.md)에 아직 반영되어 있지 않으므로 구현 전 반영이 필요하다.
- **404 오류 문구(확정)**: 이미 구현된 상세 조회(003)·수정(004)과 일관되도록 "존재하지 않거나 삭제된 티켓입니다"로 확정했다(사용자 결정). 이에 맞춰 `docs/API_SPEC.md` 5번 섹션, `docs/TEST_CASES.md`(TC-API-005-06), `docs/REQUIREMENTS.md`(FR-005)의 문구를 수정했다. 삭제 API(FR-006)의 "존재하지 않는 티켓입니다"는 이번 범위 밖이라 변경하지 않았다.
- 백로그(BACKLOG) 상태의 할 일도 완료 처리할 수 있는 것으로 가정한다. `docs/API_SPEC.md`는 "DONE으로 이동"만 정의하고 출발 상태를 제한하지 않으며, `docs/TEST_CASES.md`는 할 일·진행 중 상태만 예시로 든다.
- 완료 처리는 완료 시각을 새로 기록하는 것 외에 시작 시각(startedAt)을 변경하지 않는다(`docs/DATA_MODEL.md` 5.1).
- 보드의 완료 칼럼 24시간 노출 제한, 완료 칼럼에서 다른 칼럼으로 되돌릴 때의 완료 시각 초기화, 상태/순서 변경(`PATCH /api/tickets/reorder`), 삭제는 이번 기능의 범위 밖이다.
- 화면(프론트엔드)에서 드래그앤드롭으로 완료 칼럼에 놓았을 때 이 기능을 호출하는 연동은 이번 기능의 범위 밖이며, 이 기능은 서버가 제공하는 완료 처리 동작만 정의한다.
- MVP 단계에서는 별도의 로그인/인증 없이 단일 사용자가 사용하는 것을 전제로 한다 (`001-create-ticket-api`와 동일).
