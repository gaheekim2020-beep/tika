# Feature Specification: 티켓 상세 조회 API

**Feature Branch**: `[003-get-ticket-detail]`

**Created**: 2026-09-29

**Status**: Draft

**Input**: User description: "API_SPEC.md의 GET /api/tickets/:id 티켓 상세 조회 명세를 확인하고 구현에 필요한 요구사항을 정리해줘."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 티켓 상세 정보 확인 (Priority: P1)

사용자는 보드에서 특정 할 일 카드를 선택했을 때, 그 할 일의 모든 상세 정보(설명, 우선순위, 일정 등)를 확인하고 싶어한다. 보드 목록에는 요약 정보만 표시되므로, 개별 할 일을 자세히 살펴보려면 단건 조회가 필요하다.

**Why this priority**: 이미 구현된 목록 조회(GET /api/tickets)와 생성(POST /api/tickets)이 실사용 가치를 가지려면, 사용자가 특정 항목을 선택해 자세히 볼 수 있는 기능이 필수적이다. 상세 조회 없이는 수정/완료 등 후속 기능(FR-004, FR-005)의 전제 조건도 충족되지 않는다.

**Independent Test**: 상세 정보가 채워진 티켓을 하나 만들어 둔 뒤 해당 ID로 조회했을 때, 모든 필드(지연 여부 포함)가 정확히 반환되는지 확인하는 것만으로 독립적으로 테스트 가능하다.

**Acceptance Scenarios**:

1. **Given** 특정 ID의 할 일이 존재하는 상태에서, **When** 사용자가 해당 ID로 상세 조회를 요청하면, **Then** 해당 할 일의 모든 필드(지연 여부 포함)가 반환된다.
2. **Given** 완료 처리된 지 24시간이 지나 보드 목록에는 더 이상 보이지 않는 할 일이 존재하는 상태에서, **When** 사용자가 해당 ID로 상세 조회를 요청하면, **Then** 목록 조회와 달리 해당 할 일이 정상적으로 조회된다.

---

### User Story 2 - 존재하지 않는 항목 조회 시 안내 (Priority: P2)

사용자(또는 클라이언트 화면)는 삭제되었거나 존재한 적 없는 ID로 상세 조회를 시도했을 때, 명확하게 "존재하지 않는다"는 안내를 받고 싶어한다.

**Why this priority**: 정상 조회(P1)가 핵심 가치지만, 잘못된 접근에 대한 명확한 실패 응답이 없으면 클라이언트가 빈 화면이나 예기치 않은 오류로 사용자에게 혼란을 줄 수 있다.

**Independent Test**: 존재하지 않는 ID로 조회를 요청했을 때 명확한 "찾을 수 없음" 응답이 오는지 확인하는 것으로 독립적으로 테스트 가능하다.

**Acceptance Scenarios**:

1. **Given** 어떤 할 일도 존재하지 않는 ID가 주어진 상태에서, **When** 사용자가 해당 ID로 상세 조회를 요청하면, **Then** 시스템은 "존재하지 않는 할 일"임을 명확히 안내한다.

---

### User Story 3 - 잘못된 형식의 식별자 요청 처리 (Priority: P3)

사용자(또는 클라이언트 화면)가 숫자가 아니거나 유효하지 않은 형식의 식별자로 조회를 시도했을 때, 시스템이 이를 걸러내고 명확한 오류를 안내받고 싶어한다.

**Why this priority**: 드물게 발생하지만(잘못된 링크, URL 직접 조작 등), 식별자 형식 자체가 잘못된 경우를 처리하지 않으면 예상치 못한 서버 오류로 이어질 수 있다. P1, P2 다음으로 다뤄도 되는 방어적 시나리오다.

**Independent Test**: 숫자가 아니거나 0/음수인 식별자로 조회를 요청했을 때, 명확한 "잘못된 요청" 응답이 오는지 확인하는 것으로 독립적으로 테스트 가능하다.

**Acceptance Scenarios**:

1. **Given** 식별자가 숫자 형식이 아닌 상태에서, **When** 사용자가 상세 조회를 요청하면, **Then** 시스템은 식별자가 유효하지 않다고 안내한다.
2. **Given** 식별자가 0 이하의 숫자인 상태에서, **When** 사용자가 상세 조회를 요청하면, **Then** 시스템은 식별자가 유효하지 않다고 안내한다.

---

### Edge Cases

- 완료된 지 24시간이 지나 보드 목록에서는 사라진 할 일을 상세 조회하면 어떻게 되는가? → 목록 조회의 24시간 필터는 상세 조회에는 적용되지 않으며, 정상적으로 조회된다.
- 삭제된 할 일을 상세 조회하면 어떻게 되는가? → 존재하지 않는 할 일과 동일하게 "찾을 수 없음"으로 처리된다.
- 데이터베이스 연결 실패 등 예상치 못한 오류가 발생하면 어떻게 되는가? → 사용자에게 상세 정보를 불러오지 못했다는 일반적인 오류 안내가 표시된다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 사용자가 식별자(ID)를 지정해 특정 할 일 하나의 전체 상세 정보를 조회할 수 있게 해야 한다.
- **FR-002**: 시스템은 조회 시점을 기준으로 지연(기한 초과) 여부를 계산해 상세 정보에 포함해야 한다.
- **FR-003**: 시스템은 목록 조회에 적용되는 "완료 후 24시간 경과 시 숨김" 규칙을 상세 조회에는 적용하지 않아야 한다 — 완료된 지 오래된 할 일도 하드 삭제되지 않는 한 상세 조회로는 확인 가능해야 한다.
- **FR-004**: 시스템은 존재하지 않거나 삭제된 식별자로 조회를 요청받으면, 명확한 "찾을 수 없음" 응답을 반환해야 한다.
- **FR-005**: 시스템은 식별자가 숫자가 아니거나 양의 정수가 아니면, 조회를 시도하지 않고 "유효하지 않은 식별자" 응답을 반환해야 한다.
- **FR-006**: 시스템은 예기치 못한 내부 오류로 조회가 실패한 경우, 사용자에게 상세 정보를 불러오지 못했다는 일반적인 오류를 안내해야 한다.

### Key Entities

- **할 일 항목(Ticket)**: `001-create-ticket-api`, `002-list-tickets-api`에서 정의된 것과 동일한 엔티티. 이번 기능은 새 필드를 추가하지 않고, 식별자 하나로 단건 조회하는 책임만 가진다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 사용자는 유효한 식별자로 요청했을 때 해당 할 일의 전체 상세 정보를 한 번의 조회로 확인할 수 있다.
- **SC-002**: 완료된 지 오래되어 보드 목록에서 보이지 않는 할 일도 상세 조회로는 100% 확인 가능하다.
- **SC-003**: 존재하지 않는 식별자로 조회했을 때 100% 명확한 "찾을 수 없음" 응답을 받는다 (빈 성공 응답이나 서버 오류로 오인되지 않는다).
- **SC-004**: 잘못된 형식의 식별자로 조회했을 때 100% 명확한 "잘못된 요청" 응답을 받는다.

## Assumptions

- 이번 기능은 `001-create-ticket-api`, `002-list-tickets-api`에서 정의된 할 일 항목(Ticket) 데이터 구조를 그대로 사용하며, 새로운 데이터 항목을 추가하지 않는다.
- 식별자는 양의 정수(숫자)로 가정하며, 문자열 기반 식별자(UUID 등)는 이번 기능의 범위 밖이다.
- 삭제 기능(FR-006, `US-008`)은 아직 별도로 구현되지 않았으므로, 이번 기능에서 "삭제된 할 일"은 "존재하지 않는 식별자"와 동일하게 취급한다 (하드 삭제 기준).
- MVP 단계에서는 별도의 로그인/인증 없이 단일 사용자가 사용하는 것을 전제로 한다 (`001-create-ticket-api`와 동일).
