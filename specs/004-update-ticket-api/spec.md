**Feature Branch**: `[004-update-ticket-api]`

**Created**: 2026-09-29

**Status**: Draft

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 할 일 내용 부분 수정 (Priority: P1)

사용자는 이미 만들어 둔 할 일의 제목, 설명, 우선순위, 시작예정일, 종료예정일 중 바꾸고 싶은 항목만 골라 수정하고 싶어한다. 요구사항이 바뀌었을 때 할 일을 지우고 다시 만들 필요 없이, 필요한 부분만 고쳐서 보드에 바로 반영하고 싶다.

**Why this priority**: 생성(001), 목록(002), 상세 조회(003)까지 구현된 지금, 수정은 US-007(할 일 수정)의 핵심이자 보드를 실제로 운영하기 위한 필수 기능이다. 수정이 없으면 오타 하나 고치려고도 할 일을 삭제 후 재생성해야 한다.

**Independent Test**: 상세 정보가 채워진 할 일을 하나 만든 뒤, 제목만 바꿔서 수정 요청을 보냈을 때 제목만 변경되고 나머지 항목은 그대로이며 최종 수정 시각이 갱신되는지 확인하는 것만으로 독립적으로 테스트 가능하다.

**Acceptance Scenarios**:

1. **Given** 제목·설명·우선순위·일정이 채워진 할 일이 존재하는 상태에서, **When** 사용자가 제목만 새 값으로 수정을 요청하면, **Then** 제목만 바뀌고 나머지 항목은 기존 값을 유지하며 최종 수정 시각이 갱신된 할 일이 반환된다.
2. **Given** 할 일이 존재하는 상태에서, **When** 사용자가 제목·설명·우선순위·시작예정일·종료예정일을 한 번에 수정하면, **Then** 전달한 모든 항목이 반영된 할 일이 반환된다.
3. **Given** 종료예정일이 바뀌는 수정이 있을 때, **When** 수정된 할 일이 반환되면, **Then** 지연(기한 초과) 여부는 수정된 종료예정일과 현재 시각을 기준으로 다시 계산되어 포함된다.

---

### User Story 2 - 설정된 값 비우기 및 빈 수정 요청 (Priority: P2)

사용자는 이미 입력해 둔 설명이나 일정을 "값 없음"으로 되돌리고 싶어한다. 또한 아무 항목도 바꾸지 않는 수정 요청(예: 저장 버튼만 누른 경우)이 오류 없이 처리되길 기대한다.

**Why this priority**: 값을 채우는 수정(P1)이 핵심이지만, 한 번 입력한 설명이나 일정을 지울 수 없으면 사용자가 잘못 입력한 값을 되돌릴 방법이 없다. 다만 P1 없이는 의미가 없으므로 그다음 우선순위다.

**Independent Test**: 설명과 시작예정일이 있는 할 일에 해당 항목을 "값 없음"으로 지정해 수정을 요청했을 때 두 항목이 비워지는지, 그리고 빈 요청을 보냈을 때 기존 값이 그대로이며 최종 수정 시각만 갱신되는지 확인하는 것으로 독립적으로 테스트 가능하다.

**Acceptance Scenarios**:

1. **Given** 설명이 입력되어 있는 할 일이 존재하는 상태에서, **When** 사용자가 설명을 "값 없음"으로 지정해 수정을 요청하면, **Then** 설명이 비워진 할 일이 반환된다.
2. **Given** 시작예정일이 입력되어 있는 할 일이 존재하는 상태에서, **When** 사용자가 시작예정일을 "값 없음"으로 지정해 수정을 요청하면, **Then** 시작예정일이 비워진 할 일이 반환된다.
3. **Given** 할 일이 존재하는 상태에서, **When** 사용자가 아무 항목도 지정하지 않은 빈 수정 요청을 보내면, **Then** 기존 값이 모두 유지되고 최종 수정 시각만 갱신된 할 일이 반환된다.

### User Story 3 - 잘못된 입력값 거절 (Priority: P2)

사용자는 유효하지 않은 값(공백뿐인 제목, 너무 긴 제목/설명, 허용되지 않는 우선순위, 이미 지난 종료예정일)으로 수정을 시도했을 때, 어떤 항목이 왜 잘못되었는지 안내받고 기존 데이터는 바뀌지 않기를 기대한다.

**Why this priority**: 생성 때와 같은 입력 규칙이 수정에도 일관되게 적용되지 않으면, 수정 경로로 잘못된 데이터가 들어와 보드가 오염된다. 정상 수정(P1) 다음으로 데이터 품질을 지키는 필수 방어선이다.

**Independent Test**: 각 검증 규칙을 위반하는 값으로 수정을 요청했을 때, 문제 항목과 안내 문구가 담긴 "잘못된 요청" 응답이 오고 할 일의 기존 값이 그대로인지 확인하는 것으로 독립적으로 테스트 가능하다.

**Acceptance Scenarios**:

1. **Given** 할 일이 존재하는 상태에서, **When** 사용자가 제목을 공백만으로 수정하려 하면, **Then** "제목을 입력해주세요" 안내와 함께 제목 항목이 문제임이 표시되고 할 일은 변경되지 않는다.
2. **Given** 할 일이 존재하는 상태에서, **When** 사용자가 제목을 200자 초과로 수정하려 하면, **Then** "제목은 200자 이내로 입력해주세요" 안내와 함께 제목 항목이 문제임이 표시되고 할 일은 변경되지 않는다.
3. **Given** 할 일이 존재하는 상태에서, **When** 사용자가 설명을 1000자 초과로 수정하려 하면, **Then** "설명은 1000자 이내로 입력해주세요" 안내와 함께 설명 항목이 문제임이 표시되고 할 일은 변경되지 않는다.
4. **Given** 할 일이 존재하는 상태에서, **When** 사용자가 허용되지 않는 우선순위 값으로 수정하려 하면, **Then** "우선순위는 LOW, MEDIUM, HIGH 중 선택해주세요" 안내와 함께 우선순위 항목이 문제임이 표시되고 할 일은 변경되지 않는다.
5. **Given** 할 일이 존재하는 상태에서, **When** 사용자가 종료예정일을 오늘보다 이전 날짜로 수정하려 하면, **Then** "종료예정일은 오늘 이후 날짜를 선택해주세요" 안내와 함께 종료예정일 항목이 문제임이 표시되고 할 일은 변경되지 않는다.

---

### User Story 4 - 존재하지 않는 항목·잘못된 식별자 수정 시도 처리 (Priority: P3)

사용자(또는 클라이언트 화면)는 삭제되었거나 존재한 적 없는 할 일, 혹은 형식이 잘못된 식별자로 수정을 시도했을 때 명확한 실패 안내를 받고 싶어한다.

**Why this priority**: 드물게 발생하는 방어적 시나리오(오래 열려 있던 화면, 잘못된 링크 등)이며, 정상 수정과 입력 검증이 먼저 갖춰져야 의미가 있다.

**Independent Test**: 존재하지 않는 식별자와 숫자가 아니거나 0/음수인 식별자로 각각 수정을 요청했을 때, "찾을 수 없음"과 "유효하지 않은 식별자" 응답이 각각 오는지 확인하는 것으로 독립적으로 테스트 가능하다.

**Acceptance Scenarios**:

1. **Given** 어떤 할 일도 존재하지 않는 식별자가 주어진 상태에서, **When** 사용자가 수정을 요청하면, **Then** 시스템은 "존재하지 않거나 삭제된 할 일"임을 명확히 안내한다.
2. **Given** 식별자가 숫자 형식이 아니거나 0 이하인 상태에서, **When** 사용자가 수정을 요청하면, **Then** 시스템은 식별자가 유효하지 않다고 안내한다.

---

### Edge Cases

- 상태(status)나 순서(position) 값을 수정 요청에 함께 보내면 어떻게 되는가? → 이 기능의 처리 대상이 아니므로 해당 값은 반영되지 않으며 할 일의 실제 상태와 순서는 바뀌지 않는다. (상태/순서 변경은 별도 기능이 담당)
- 이미 완료(DONE)된 할 일도 수정할 수 있는가? → 별도 제한이 명세에 없으므로 다른 상태와 동일하게 수정할 수 있다.
- 종료예정일을 이미 지난 날짜로 가진 기존 할 일의 제목만 수정하면 어떻게 되는가? → 종료예정일이 요청에 포함되지 않았으므로 종료예정일 검증은 적용되지 않고 제목 수정은 정상 처리된다.
- 요청 본문이 올바른 형식(JSON)이 아니면 어떻게 되는가? → 검증 실패로 간주해 "잘못된 요청"으로 안내하며 할 일은 변경되지 않는다.
- 여러 항목을 동시에 수정하는데 그중 하나만 유효하지 않으면 어떻게 되는가? → 전체 요청이 거절되고 어떤 항목도 반영되지 않는다(일부만 반영되지 않는다).
- 두 화면에서 같은 할 일을 차례로 수정하면 어떻게 되는가? → 나중 요청이 반영되며, 서로 겹치지 않는 항목은 두 수정 내용이 모두 남는다(항목 단위 부분 수정).
- 데이터베이스 연결 실패 등 예상치 못한 오류가 발생하면 어떻게 되는가? → 사용자에게 수정하지 못했다는 일반적인 오류 안내가 표시되고 할 일은 변경되지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 사용자가 식별자로 지정한 할 일 하나에 대해 제목, 설명, 우선순위, 시작예정일, 종료예정일을 수정할 수 있게 해야 한다.
- **FR-002**: 시스템은 수정 요청에 포함된 항목만 갱신하고, 포함되지 않은 항목은 기존 값을 그대로 유지해야 한다(부분 수정).
- **FR-003**: 시스템은 수정이 성공할 때마다 최종 수정 시각을 현재 시각으로 갱신해야 한다. 아무 항목도 지정하지 않은 빈 수정 요청도 성공으로 처리하며 이때도 최종 수정 시각은 갱신한다.
- **FR-004**: 시스템은 설명, 시작예정일, 종료예정일을 "값 없음"으로 명시해 비울 수 있게 해야 한다. 제목과 우선순위는 항상 값을 가져야 하므로 비울 수 없다.
- **FR-005**: 시스템은 수정된 결과를 반환할 때, 수정된 종료예정일과 현재 시각을 기준으로 지연(기한 초과) 여부를 다시 계산해 포함해야 한다.
- **FR-006**: 시스템은 제목이 공백만이거나 비어 있으면 거절하고 "제목을 입력해주세요"를, 200자를 초과하면 "제목은 200자 이내로 입력해주세요"를 제목 항목과 함께 안내해야 한다.
- **FR-007**: 시스템은 설명이 1000자를 초과하면 거절하고 "설명은 1000자 이내로 입력해주세요"를 설명 항목과 함께 안내해야 한다.
- **FR-008**: 시스템은 우선순위가 LOW, MEDIUM, HIGH 이외의 값이면 거절하고 "우선순위는 LOW, MEDIUM, HIGH 중 선택해주세요"를 우선순위 항목과 함께 안내해야 한다.
- **FR-009**: 시스템은 종료예정일이 오늘보다 이전 날짜이면 거절하고 "종료예정일은 오늘 이후 날짜를 선택해주세요"를 종료예정일 항목과 함께 안내해야 한다. 종료예정일이 요청에 포함되지 않은 경우에는 이 검증을 적용하지 않는다.
- **FR-010**: 시스템은 하나 이상의 입력값이 유효하지 않으면 요청 전체를 거절하고 어떤 항목도 반영하지 않아야 한다.
- **FR-011**: 시스템은 상태(status)와 순서(position)를 이 기능으로 변경하지 않아야 한다. 요청에 이 값들이 포함되어도 할 일의 실제 상태와 순서는 바뀌지 않는다.
- **FR-012**: 시스템은 존재하지 않거나 삭제된 식별자로 수정을 요청받으면, 명확한 "찾을 수 없음" 응답을 반환하고 어떤 데이터도 변경하지 않아야 한다.
- **FR-013**: 시스템은 식별자가 숫자가 아니거나 양의 정수가 아니면, 수정을 시도하지 않고 "유효하지 않은 식별자" 응답을 반환해야 한다.
- **FR-014**: 시스템은 요청 본문이 올바른 형식이 아니면 검증 실패로 처리해 "잘못된 요청"으로 안내해야 한다.
- **FR-015**: 시스템은 예기치 못한 내부 오류로 수정이 실패한 경우, 사용자에게 수정하지 못했다는 일반적인 오류를 안내하고 할 일을 변경하지 않아야 한다.

### Key Entities

- **할 일 항목(Ticket)**: `001-create-ticket-api`, `002-list-tickets-api`, `003-get-ticket-detail`에서 정의된 것과 동일한 엔티티. 이번 기능은 새 필드를 추가하지 않고, 기존 항목 중 제목·설명·우선순위·시작예정일·종료예정일만 수정하며, 최종 수정 시각과 지연 여부(조회 시점에 계산되는 파생 값)에 영향을 준다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 사용자는 유효한 값으로 수정을 요청했을 때 한 번의 요청으로 원하는 항목만 바꾸고, 바꾸지 않은 항목은 100% 기존 값으로 유지됨을 확인할 수 있다.
- **SC-002**: 수정에 성공한 모든 요청(빈 요청 포함)에서 최종 수정 시각이 갱신되고 지연 여부가 수정 결과 기준으로 다시 계산되어 반환된다.
- **SC-003**: 유효하지 않은 입력으로 수정을 요청한 경우 100% 문제 항목과 안내 문구가 함께 표시되고, 할 일의 기존 값은 하나도 바뀌지 않는다.
- **SC-004**: 존재하지 않는 식별자 또는 형식이 잘못된 식별자로 수정을 요청한 경우 100% 각각 "찾을 수 없음"/"유효하지 않은 식별자" 응답을 받으며, 빈 성공 응답이나 서버 오류로 오인되지 않는다.
- **SC-005**: 상태·순서 값을 함께 보낸 수정 요청 후에도 해당 할 일의 상태와 순서는 100% 이전과 동일하다.

## Assumptions

- 이번 기능은 `001-create-ticket-api`, `002-list-tickets-api`, `003-get-ticket-detail`에서 정의된 할 일 항목(Ticket) 데이터 구조와 검증 규칙(제목 1~200자, 설명 최대 1000자, 우선순위 3종, 종료예정일 오늘 이후)을 그대로 사용하며 새로운 데이터 항목을 추가하지 않는다.
- 비울 수 있는 항목의 범위: `docs/TEST_CASES.md`(TC-API-004-03, 004-04)는 설명과 시작예정일을 "값 없음"으로 되돌리는 경우를 정의하고, `docs/API_SPEC.md`는 설명만 `null`을 명시한다. 종료예정일은 문서에 명시가 없지만 사용자가 잘못 입력한 종료예정일을 되돌릴 방법이 필요하다고 보아 시작예정일과 동일하게 비울 수 있는 것으로 가정한다. 이 가정은 명세 확정 전 검토가 필요하다.
- 날짜 항목(시작예정일·종료예정일)은 `docs/API_SPEC.md`와 생성 기능(001)에 맞춰 날짜(연-월-일) 형식으로 가정한다. `docs/REQUIREMENTS.md`(FR-004)에는 "날짜/시간 형식"으로 적혀 있어 문서 간 표현 차이가 있다.
- 상태(status)·순서(position)가 수정 요청에 포함되면 오류로 거절하지 않고 무시하는 것으로 가정한다. `docs/TEST_CASES.md`(TC-API-004-12)는 "무시 또는 거부" 둘 다 허용하며, 어느 쪽이든 실제 상태와 순서가 바뀌지 않는다는 결과는 같다.
- 시작예정일과 종료예정일 사이의 선후 관계(시작이 종료보다 늦은 경우)는 명세에 규칙이 없으므로 이번 기능에서 검증하지 않는다.
- 완료(DONE) 상태의 할 일에 대한 수정 제한은 명세에 없으므로 다른 상태와 동일하게 수정할 수 있다고 가정한다.
- 상태/순서 변경(`PATCH /api/tickets/reorder`), 완료 처리(`PATCH /api/tickets/:id/complete`), 삭제는 이번 기능의 범위 밖이다.
- MVP 단계에서는 별도의 로그인/인증 없이 단일 사용자가 사용하는 것을 전제로 한다 (`001-create-ticket-api`와 동일).
