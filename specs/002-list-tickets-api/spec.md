# Feature Specification: 티켓 목록 조회 API (보드)

**Feature Branch**: `[002-list-tickets-api]`

**Created**: 2026-09-25

**Status**: Draft

**Input**: User description: "docs/API_SPEC.md에서 GET /api/tickets 명세를 확인하고 구현에 필요한 요구사항을 정리해줘."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 칸반 보드 현황 파악 (Priority: P1)

사용자는 보드 화면에 진입했을 때 모든 할 일이 진행 단계별(할 일 목록/진행 예정/진행 중/완료) 칼럼으로 나뉘어 한눈에 보이길 원한다. 그래야 전체 업무 현황을 즉시 파악할 수 있다.

**Why this priority**: 목록 조회 없이는 생성된 티켓을 화면에서 확인할 방법이 없다. 이미 구현된 등록(POST) 기능이 실사용 가치를 가지려면 조회 기능이 필수 짝이며, 보드 자체가 이 앱의 핵심 화면이다.

**Independent Test**: 여러 상태에 걸쳐 티켓을 미리 만들어 둔 뒤 목록을 조회했을 때, 4개 칼럼으로 정확히 그룹화되어 각 칼럼 내 순서가 올바르게 반환되는지 확인하는 것만으로 독립적으로 테스트 가능하다.

**Acceptance Scenarios**:

1. **Given** 4개 칼럼(할 일 목록/진행 예정/진행 중/완료) 모두에 티켓이 하나 이상 있는 상태에서, **When** 사용자가 보드를 조회하면, **Then** 각 칼럼에 해당 상태의 티켓만 모여서 표시된다.
2. **Given** 같은 칼럼에 순서가 다른 티켓이 여러 개 있는 상태에서, **When** 사용자가 보드를 조회하면, **Then** 해당 칼럼의 티켓이 지정된 순서(먼저 보여야 할 것이 위) 그대로 표시된다.
3. **Given** 등록된 티켓이 하나도 없는 상태에서, **When** 사용자가 보드를 조회하면, **Then** 4개 칼럼 모두 비어 있는 상태로 정상 표시된다(오류 없음).
4. **Given** 완료 처리된 지 얼마 되지 않은(24시간 이내) 티켓이 있는 상태에서, **When** 사용자가 보드를 조회하면, **Then** 해당 티켓이 완료 칼럼에 표시된다.
5. **Given** 완료 처리된 지 오래된(24시간 초과) 티켓이 있는 상태에서, **When** 사용자가 보드를 조회하면, **Then** 해당 티켓은 완료 칼럼을 포함한 어떤 칼럼에도 표시되지 않는다.

---

### User Story 2 - 마감 초과 인지 (Priority: P2)

사용자는 보드를 보는 즉시 종료예정일이 지난 할 일을 식별해, 지연된 업무를 우선 처리하고 싶어한다.

**Why this priority**: 목록이 보이는 것(P1) 자체는 동작하지만, 지연 여부 표시가 없으면 사용자가 어떤 일이 급한지 판단하려면 각 티켓의 날짜를 일일이 확인해야 한다. 조회 API의 부가 가치이자 US-004(마감 초과 인지)의 데이터 기반이다.

**Independent Test**: 종료예정일이 과거인 티켓과 미래인 티켓을 각각 만들어 조회했을 때, 지연 여부 표시가 조건에 맞게 정확히 계산되어 내려오는지 확인하는 것으로 독립적으로 테스트 가능하다.

**Acceptance Scenarios**:

1. **Given** 완료되지 않았고 종료예정일이 어제인 티켓이 할 일 목록 칼럼에 있는 상태에서, **When** 사용자가 보드를 조회하면, **Then** 해당 티켓에 지연 표시가 함께 내려온다.
2. **Given** 완료되지 않았고 종료예정일이 어제인 티켓이 진행 예정 또는 진행 중 칼럼에 있는 상태에서, **When** 사용자가 보드를 조회하면, **Then** 해당 티켓에 지연 표시가 함께 내려온다.
3. **Given** 종료예정일이 어제인 티켓이 완료 칼럼에 있는 상태에서(완료 처리됨), **When** 사용자가 보드를 조회하면, **Then** 완료된 티켓이므로 지연 표시는 되지 않는다.
4. **Given** 종료예정일이 지정되지 않은 티켓이 있는 상태에서, **When** 사용자가 보드를 조회하면, **Then** 해당 티켓은 지연 표시가 되지 않는다.

---

### Edge Cases

- 데이터베이스 연결 실패 등 예상치 못한 오류가 발생하면 어떻게 되는가? → 사용자에게 목록을 불러오지 못했다는 일반적인 오류 안내가 표시되고, 부분적으로만 채워진 결과는 반환하지 않는다.
- 어떤 칼럼에 티켓이 전혀 없으면 어떻게 되는가? → 해당 칼럼은 빈 목록으로 정상 표시되며 오류로 취급하지 않는다.
- 완료된 지 정확히 24시간이 되는 경계 시점의 티켓은 어떻게 되는가? → 24시간 이내에 포함되면 완료 칼럼에 표시되고, 초과하면 어떤 칼럼에도 나타나지 않는다.
- 조회 요청에 별도 조건(파라미터)을 지정할 수 있는가? → 이번 기능은 조건 없이 전체 목록을 조회하는 것만 다룬다. 필터링/검색은 범위 밖이다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 사용자가 별도 조건 없이 전체 할 일 목록을 한 번에 조회할 수 있게 해야 한다.
- **FR-002**: 시스템은 조회 결과를 4개 상태(할 일 목록/진행 예정/진행 중/완료) 그룹으로 분류해 반환해야 한다.
- **FR-003**: 시스템은 각 칼럼 내 할 일 순서를 지정된 정렬 순서(먼저 보여야 할 것이 앞)대로 반환해야 한다.
- **FR-004**: 시스템은 완료 칼럼에는 완료 처리된 지 24시간 이내인 할 일만 포함해야 하며, 그보다 오래된 완료 항목은 목록에서 제외해야 한다.
- **FR-005**: 시스템은 조회되는 각 할 일에 대해 지연(기한 초과) 여부를 함께 계산해 반환해야 한다.
- **FR-006**: 시스템은 완료되지 않았고 종료예정일이 현재 시점보다 과거인 할 일만 지연 상태로 판정해야 한다.
- **FR-007**: 시스템은 완료된 할 일은 종료예정일이 과거라도 지연 상태로 판정하지 않아야 한다.
- **FR-008**: 시스템은 종료예정일이 지정되지 않은 할 일은 지연 상태로 판정하지 않아야 한다.
- **FR-009**: 시스템은 등록된 할 일이 하나도 없어도 오류 없이 빈 상태의 4개 칼럼을 반환해야 한다.
- **FR-010**: 시스템은 예기치 못한 내부 오류로 조회가 실패한 경우, 사용자에게 목록을 불러오지 못했다는 일반적인 오류를 안내해야 한다.

### Key Entities

- **할 일 항목(Ticket)**: `001-create-ticket-api`에서 정의된 것과 동일한 엔티티. 이번 기능은 새 필드를 추가하지 않고, 기존 항목을 상태별로 그룹화·정렬해 조회하고 지연 여부를 실시간으로 계산해 함께 내려주는 책임만 가진다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 사용자는 보드에 진입한 즉시(별도 조작 없이) 전체 할 일 현황을 4개 칼럼으로 구분해 확인할 수 있다.
- **SC-002**: 각 칼럼 내 할 일은 항상 지정된 순서대로 표시되어, 사용자가 위에서 아래로 읽을 때 순서가 뒤바뀌어 보이는 경우가 없다.
- **SC-003**: 기한이 지난 미완료 할 일은 목록 조회 결과만으로 100% 식별 가능하다 (별도 계산이나 추가 조회 불필요).
- **SC-004**: 완료된 지 오래된 항목이 보드에 계속 남아 화면을 어지럽히는 경우가 없다 — 24시간이 지나면 목록에서 자동으로 사라진다.
- **SC-005**: 할 일이 하나도 없는 초기 상태에서도 보드 조회가 오류 없이 정상 동작한다.

## Assumptions

- 이번 기능은 `001-create-ticket-api`에서 정의된 할 일 항목(Ticket) 데이터 구조를 그대로 사용하며, 새로운 데이터 항목을 추가하지 않는다.
- "24시간 이내 완료"의 기준 시각은 조회가 실행되는 시점(현재 시각)이며, 시간대 처리는 별도로 명세하지 않는다 (`001-create-ticket-api`의 날짜 비교 가정과 동일).
- 페이지네이션, 정렬 조건 변경, 필터링(상태/우선순위 등 조건 검색)은 이번 기능 범위에 포함하지 않는다 — 전체 목록을 한 번에 반환하는 것만 다룬다.
- MVP 단계에서는 별도의 로그인/인증 없이 단일 사용자가 사용하는 것을 전제로 한다 (`001-create-ticket-api`와 동일).
- 삭제된 티켓은 조회 대상에서 항상 제외된다는 것을 전제로 하며, 삭제 기능 자체의 동작 방식은 이번 기능의 범위 밖이다.
