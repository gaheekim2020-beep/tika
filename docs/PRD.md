## 1. 제품 개요

**Tika**는 티켓 기반 칸반 보드 형태의 개인용 TODO 관리 웹앱이다.

사용자는 할 일을 "티켓" 단위로 등록하고, `Backlog → TODO → In Progress → Done`의 4단계 칼럼 사이를 드래그 앤 드롭으로 이동시키며 업무 진행 상황을 시각적으로 관리한다. 복잡한 프로젝트 관리 도구 대신, 개인이 빠르게 할 일을 기록하고 상태를 옮기는 것만으로 진행 현황을 한눈에 파악할 수 있는 가벼운 도구를 지향한다.

### 제품 목표
- 할 일 등록의 마찰을 최소화한다 (제목만으로 즉시 생성 가능).
- 드래그 앤 드롭으로 상태 변경을 직관적으로 처리한다.
- 계획일/실제일을 구분 기록하여 지연(Overdue) 여부를 자동으로 파악할 수 있게 한다.

### 대상 사용자
- 개인 업무를 칸반 보드로 관리하고 싶은 1인 사용자 (MVP는 단일 사용자 전제, 로그인 없음).

## 2. MVP 범위

| 구분 | 내용 |
|------|------|
| 사용자 모델 | 단일 사용자 (인증 없음, 별도 계정 개념 없음) |
| 보드 구조 | 고정 4칼럼: `Backlog` / `TODO` / `In Progress` / `Done` (커스텀 칼럼 불가) |
| 티켓 기능 | 생성 / 조회(목록·상세) / 수정 / 삭제 (CRUD 전체) |
| 상태 변경 | 드래그 앤 드롭으로 칼럼 간 이동 및 칼럼 내 순서 변경 |
| 날짜 필드 | 계획시작일(`plannedStartDate`), 시작일(`startedAt`, 자동), 계획종료일(`dueDate`), 종료일(`completedAt`, 자동) |
| 부가 기능 | 우선순위(LOW/MEDIUM/HIGH), Overdue(지연) 자동 판정 및 시각적 표시 |

날짜 필드는 사용자가 직접 입력하는 **계획일**과 시스템이 상태 변경 시 자동 기록하는 **실적일**로 구분된다.

| 필드 | 입력 주체 | 기록 시점 |
|------|-----------|-----------|
| plannedStartDate | 사용자 입력 | 생성/수정 시 |
| dueDate (계획종료일) | 사용자 입력 | 생성/수정 시 |
| startedAt (시작일) | 시스템 자동 | TODO 칼럼 진입 시 |
| completedAt (종료일) | 시스템 자동 | Done 칼럼 진입 시 |

## 3. 2차 스펙 (MVP 제외 범위)

아래 항목은 명세에 없는 기능으로, MVP 개발 범위에서 **명시적으로 제외**한다.

- 사용자 인증 / 로그인 / 세션 관리
- 커스텀 칼럼 추가/삭제/이름 변경 (4칼럼 고정)
- 멀티 사용자 지원 (팀/워크스페이스, 담당자 지정 등)
- 라벨(태그) 기능
- 코멘트/댓글 기능
- 파일 업로드 / 첨부
- 검색 (제목/설명 기반 티켓 검색)
- 필터링 (예: "이번주 업무", "일정이 초과된 업무" 등 조건별 보기)

> 위 항목은 향후 2차 스펙으로 별도 논의 및 문서화 후 진행한다.

### UI 자리 배치 방침 (검색)

기능 구현은 제외하지만, 검색 입력창(`SearchInput`)은 `docs/reference/image/tika-wireframe.png` 와이어프레임 기준 상단 헤더 위치에 **레이아웃 자리만 미리 배치**한다. MVP에서는 비활성(disabled) placeholder로만 렌더링하여, 2차 스펙에서 실제 검색 기능을 구현할 때 헤더 레이아웃을 다시 설계하지 않아도 되게 한다. 필터 탭("이번주 업무" 등)은 검색과 달리 자리조차 배치하지 않는다 — 자리를 남길지는 기능별로 개별 판단하며, 일괄 적용 규칙이 아니다.

## 4. 사용자 시나리오

핵심 사용 흐름: **할 일 등록 → 상태 이동 → 수정/삭제 → 완료 확인**

```
1. 할 일 등록
   사용자가 "새 티켓" 버튼 클릭 → 제목 입력(+선택: 설명/우선순위/계획일) → 생성
   → Backlog 칼럼 최상단에 카드 추가

2. 상태 이동
   사용자가 카드를 드래그하여 TODO로 이동
   → status: BACKLOG → TODO, startedAt 자동 기록
   → 이후 In Progress로 이동 (순서/칼럼 자유 이동, 역방향 포함)

3. 수정 / 삭제
   사용자가 카드를 클릭 → 상세 모달에서 제목/설명/우선순위/계획일 수정
   → 필요 시 삭제 버튼 → 확인 다이얼로그 → 영구 삭제

4. 완료 확인
   사용자가 카드를 Done으로 드래그
   → completedAt 자동 기록, Done 칼럼에 표시 (24시간 이내 완료 건만 노출)
   → 계획종료일이 지난 미완료 카드는 Overdue 표시로 우선 확인 가능
```

이 흐름을 통해 사용자는 별도의 학습 없이 "카드를 만들고, 옮기고, 고치고, 끝낸다"는 자연스러운 조작만으로 보드를 관리할 수 있다.

## 5. 핵심 기능 목록

REQUIREMENTS.md의 FR-001 ~ FR-008과 대응한다. 상세 입력값/검증 규칙은 [REQUIREMENTS.md](./REQUIREMENTS.md) 참조.

| FR | 기능 | 설명 |
|----|------|------|
| FR-001 | 티켓 생성 | 제목(필수) + 설명/우선순위/계획시작일/계획종료일(선택)로 티켓을 생성한다. 항상 Backlog 최상단에 추가된다. |
| FR-002 | 티켓 목록 조회 (보드) | 전체 티켓을 4개 칼럼별로 그룹화하여 조회하며, 칼럼 내 position 오름차순 정렬 및 Overdue 파생 필드를 포함해 반환한다. |
| FR-003 | 티켓 상세 조회 | 특정 티켓 ID로 전체 상세 정보(제목/설명/상태/우선순위/일자 등)를 단건 조회한다. |
| FR-004 | 티켓 수정 | 제목/설명/우선순위/계획시작일/계획종료일을 부분 수정(Partial Update)한다. status/position은 이 API에서 다루지 않는다. |
| FR-005 | 티켓 완료 | Done 칼럼 이동 시 completedAt을 자동 기록하고, Done에서 벗어나면 종료일을 초기화한다. |
| FR-006 | 티켓 삭제 | 티켓을 데이터베이스에서 완전 삭제(Hard Delete)한다. |
| FR-007 | 상태/순서 변경 (드래그앤드롭) | 칼럼 간 이동 및 칼럼 내 순서 변경을 position 재계산 로직으로 처리한다. TODO 진입 시 startedAt 자동 기록, BACKLOG 복귀 시 초기화된다. |
| FR-008 | Overdue(지연) 판정 | 계획종료일이 지났고 상태가 Done이 아닌 티켓을 조회 시점에 동적으로 계산하여 지연 표시한다. |

|------|------|-----------|
| Framework | Next.js 15 (App Router) | 프론트/백엔드를 하나의 저장소에서 App Router 기반으로 함께 개발·배포할 수 있어 개인 프로젝트 규모에 적합하고, Vercel과의 네이티브 통합으로 배포 마찰이 적다. |

| Frontend | React 19 | Next.js App Router의 기본 UI 라이브러리로, 컴포넌트 기반 구조가 칸반 보드의 칼럼/카드 계층 구조 표현에 자연스럽다. |
| Styling | Tailwind CSS 4 | 유틸리티 클래스 기반으로 빠른 UI 개발이 가능하며, 디자인 시스템(`colors.json`, CSS 변수)과 결합해 일관된 스타일을 유지하기 쉽다. |
| Drag & Drop | @dnd-kit/core + @dnd-kit/sortable | 접근성(키보드 조작, ARIA) 지원이 내장되어 있고, React와의 선언적 통합이 용이해 칼럼 간 이동 및 칼럼 내 재정렬(FR-007) 구현에 적합하다. |
| ORM | Drizzle ORM | TypeScript 우선 설계로 스키마와 타입이 자동 동기화되며, raw SQL 없이도 명시적이고 타입 안전한 쿼리를 작성할 수 있다. |
| DB | PostgreSQL (로컬: node-postgres / 배포: Vercel Postgres) | 관계형 모델(티켓-상태-순서)과 트랜잭션(position 재계산의 원자성, FR-007)이 필요한 도메인에 적합하며, Vercel 배포 환경과 서버리스 최적화가 되어 있다. |
| Validation | Zod | 프론트엔드/백엔드 양쪽에서 동일한 스키마로 이중 검증(NFR-004)하여 입력 검증 로직 중복과 불일치를 방지한다. |
| Testing | Jest + React Testing Library | TDD 워크플로우(TEST_CASES.md 기반)를 지원하며, 컴포넌트/서비스 레이어를 분리 테스트할 수 있는 생태계가 성숙해 있다. |
| Deployment | Vercel | Next.js 네이티브 배포로 git push만으로 자동 배포되며, PR별 프리뷰 배포와 HTTPS가 기본 제공되어 별도 인프라 구성이 불필요하다. |

## 8. 와이어프레임 참고

보드 레이아웃은 **좌측 Backlog 사이드바 + 우측 3컬럼 보드**의 Swimlane 구조를 따른다. Backlog는 별도 진행 단계라기보다 "대기열" 성격이 강하므로 좌측에 고정 사이드바로 분리하고, 실제 진행 단계(TODO / In Progress / Done)는 우측에 3개 칼럼으로 배치하여 작업 흐름에 집중할 수 있게 한다.

```
┌───────────────┬─────────────────────────────────────────────────────┐
│   Backlog      │   TODO          In Progress          Done          │
│  (사이드바)     │  ┌─────────┐    ┌─────────┐        ┌─────────┐     │
│                │  │ 카드 수 │    │ 카드 수 │        │ 카드 수 │     │
│ [+ 새 티켓]    │  ├─────────┤    ├─────────┤        ├─────────┤     │
│                │  │ 카드 A  │    │ 카드 D  │        │ 카드 F  │     │
│ ┌───────────┐  │  │ 카드 B  │    │ 카드 E  │        │ 카드 G  │     │
│ │ 카드 1    │  │  │ 카드 C  │    │         │        │         │     │
│ ├───────────┤  │  │         │    │         │        │         │     │
│ │ 카드 2    │  │  │         │    │         │        │         │     │
│ ├───────────┤  │  │         │    │         │        │         │     │
│ │ 카드 3 ⚠  │  │  │         │    │         │        │         │     │
│ │(Overdue)  │  │  │         │    │         │        │         │     │
│ └───────────┘  │  └─────────┘    └─────────┘        └─────────┘     │
└───────────────┴─────────────────────────────────────────────────────┘
      ↑ 드래그 앤 드롭으로 사이드바 ↔ 각 칼럼, 칼럼 ↔ 칼럼 이동 가능
```

- **Backlog 사이드바**: 신규 티켓 생성 진입점(`+ 새 티켓`)을 배치하고, 아직 착수하지 않은 대기 티켓을 세로 스크롤 목록으로 표시한다.
- **우측 3컬럼 보드**: TODO / In Progress / Done을 가로 배치하여 진행 중인 작업 흐름을 한눈에 비교할 수 있게 한다. 각 칼럼 상단에는 카드 수를 표시한다 (US-003).
- **Overdue 카드**: 계획종료일 경과 + 미완료 상태인 카드는 경고 아이콘/태그로 시각적으로 구분한다 (FR-008, US-004).
- 반응형 레이아웃(NFR-002)에서는 모바일 기준 사이드바와 칼럼이 단일 칼럼 스크롤 뷰로 전환된다.

> 상세 컴포넌트 계층과 Props는 COMPONENT_SPEC.md에서 별도 정의한다.
