## 기능 요구사항(Functional Requirements)

### FR-001: 티켓 생성

**설명**: 사용자가 새로운 티켓을 생성하여 Backlog 최상단에 추가한다.

**API 매핑**: `POST /api/tickets`

**입력 필드**:
| 필드 | 타입 | 필수 | 제약조건 | 기본값 |
|------|------|------|----------|--------|
| title | string | O | 1~200자, 공백만 불가 | - |
| description | string | X | 최대 1000자 | null |
| priority | enum | X | LOW, MEDIUM, HIGH | MEDIUM |
| plannedStartDate | date | X | ISO 8601 날짜/시간 형식 | null |
| dueDate | date | X | 오늘 이후 날짜 (과거 날짜 불가) | null |

**처리 규칙**:
- 생성 시 status는 항상 BACKLOG
- 생성 시 position은 해당 칼럼의 최댓값 + 1024 (맨 위 배치)
- 칼럼에 티켓이 없을 경우 position = 1024
- createdAt, updatedAt 자동 설정

**검증 에러 메시지**:
| 조건 | 메시지 |
|------|--------|
| 제목 누락 | "제목을 입력해주세요" |
| 제목 200자 초과 | "제목은 200자 이내로 입력해주세요" |
| 제목 공백만 입력 | "제목을 입력해주세요" |
| 설명 1000자 초과 | "설명은 1000자 이내로 입력해주세요" |
| 잘못된 우선순위 값 | "우선순위는 LOW, MEDIUM, HIGH 중 선택해주세요" |
| 과거 종료예정일 | "종료예정일은 오늘 이후 날짜를 선택해주세요" |

**성공 응답**: 201 Created + 생성된 티켓 전체 데이터  
**실패 응답**: 400 Bad Request + 검증 에러 상세

### FR-002: 티켓 목록 조회 (보드 형태)

**설명**: 보드 화면을 구성하기 위해 전체 티켓 목록을 4개 컬럼(상태)별로 그룹화하여 조회한다. 각 컬럼 내 티켓은 순서(`position` 오름차순)별로 정렬되어 반환된다.

**API 매핑**: `GET /api/tickets`

**처리 규칙**:
- 삭제되지 않은 전체 티켓을 조회한 뒤, 4개 컬럼(`BACKLOG`, `TODO`, `IN_PROGRESS`, `DONE`) 객체/배열 형태로 그룹화하여 반환
- 각 컬럼 내 티켓 정렬 순서는 `position` 오름차순(ASC)으로 정렬
- 각 티켓 반환 시 실시간으로 오버듀 여부(`isOverdue`) 파생 필드를 연산하여 포함
  - **오버듀 조건**: `status != 'DONE'` 이고 `dueDate`가 존재하며, 조회 시점 현재 시각(`now`)보다 과거인 경우 `true`, 그 외는 `false`

**응답 데이터**:
- 4개 컬럼별로 그룹화된 티켓 배열 (`BACKLOG`, `TODO`, `IN_PROGRESS`, `DONE`)
- 각 컬럼 내 정렬: `position` 오름차순
- 각 티켓에 `isOverdue` 파생 필드 포함

**성공 응답**: 200 OK + 4개 컬럼별로 그룹화된 티켓 배열 데이터  
**실패 응답**: 500 Internal Server Error + 에러 상세 정보

### FR-003: 티켓 상세 조회

**설명**: 특정 티켓 ID를 지정하여 해당 티켓의 모든 상세 정보를 단건으로 조회한다.

**API 매핑**: `GET /api/tickets/:id`

**입력 필드**: (Path Parameter)
| 필드 | 타입 | 필수 | 제약조건 | 기본값 |
|------|------|------|----------|--------|
| id | number | O | 양의 정수 | - |

**처리 규칙**:
- 요청받은 티켓 ID가 존재하지 않는 경우 `404 Not Found` 응답
- 존재할 경우 해당 티켓의 전체 정보(제목, 설명, 상태, 우선순위, 위치, 시작/종료 예정일, 생성/수정일시 등) 반환
- 조회 시점의 `dueDate`와 `status`를 기준으로 실시간 오버듀 여부(`isOverdue`) 파생 필드를 연산하여 포함
  - **오버듀 조건**: `status != 'DONE'` 이고 `dueDate`가 존재하며, 현재 시각(`now`)보다 과거인 경우 `true`, 그 외는 `false`

**검증 에러 메시지**:
| 조건 | 메시지 |
|------|--------|
| ID 형식 오류 | "유효하지 않은 티켓 ID입니다" |
| 존재하지 않는 ID | "존재하지 않거나 삭제된 티켓입니다" |

**성공 응답**: 200 OK + 단건 티켓 상세 데이터 (`isOverdue` 포함)  
**실패 응답**: 400 Bad Request (형식 오류) / 404 Not Found (티켓 없음) + 검증 에러 상세

### FR-004: 티켓 수정

**설명**: 기존 티켓의 주요 정보(제목, 설명, 우선순위, 시작/종료 예정일)를 수정한다. 필요한 필드만 선택적으로 변경할 수 있다.

**API 매핑**: `PATCH /api/tickets/:id`

**입력 필드**: (Request Body)
| 필드 | 타입 | 필수 | 제약조건 | 기본값 |
|------|------|------|----------|--------|
| title | string | X | 1~200자, 공백만 불가 | - |
| description | string | X | 최대 1000자 | - |
| priority | enum | X | LOW, MEDIUM, HIGH | - |
| plannedStartDate | string | X | ISO 8601 날짜/시간 형식 | - |
| dueDate | string | X | 오늘 이후 날짜 (과거 날짜 불가) | - |

**처리 규칙**:
- 전달된 필드만 선택적으로 업데이트 (Partial Update)
- 요청된 ID의 티켓이 존재하지 않거나 삭제된 경우 `404 Not Found` 반환
- `status` 및 `position` 변경은 본 API의 처리 대상에서 제외 (상태/순서 변경 API에서 처리)
- 수정 완료 시 `updatedAt` 필드를 현재 시각으로 자동 갱신
- 수정된 `dueDate`와 현재 시각을 기준으로 `isOverdue` 파생 필드를 재연산하여 반환

**검증 에러 메시지**:
| 조건 | 메시지 |
|------|--------|
| 제목 200자 초과 | "제목은 200자 이내로 입력해주세요" |
| 제목 공백만 입력 | "제목을 입력해주세요" |
| 설명 1000자 초과 | "설명은 1000자 이내로 입력해주세요" |
| 잘못된 우선순위 값 | "우선순위는 LOW, MEDIUM, HIGH 중 선택해주세요" |
| 과거 종료예정일 | "종료예정일은 오늘 이후 날짜를 선택해주세요" |
| 존재하지 않는 티켓 | "존재하지 않거나 삭제된 티켓입니다" |

**성공 응답**: 200 OK + 수정된 티켓 전체 데이터  
**실패 응답**: 400 Bad Request (입력값 검증 에러) / 404 Not Found (존재하지 않는 티켓) + 에러 상세

### FR-005: 티켓 완료

**설명**: 티켓을 Done 칼럼으로 이동하여 완료 처리하고, 완료 일시(`completedAt`)를 자동 설정한다.

**API 매핑**: `PATCH /api/tickets/:id/complete`

**입력 필드**: (Path Parameter)
| 필드 | 타입 | 필수 | 제약조건 | 기본값 |
|------|------|------|----------|--------|
| id | number | O | 양의 정수 | - |

**처리 규칙**:
- DONE으로 이동 시: `completedAt` = 현재 시각(`now`), `status` = `DONE`
- DONE에서 다른 칼럼으로 이동 시: `completedAt` = `null`
- Done 칼럼에는 `completedAt` 기준 24시간 이내 완료된 티켓만 표시
- 완료 처리 시 `status == 'DONE'`이 되므로 `isOverdue` 파생 필드는 `false`로 연산되어 반환
- 수정 완료 시 `updatedAt` 필드를 현재 시각으로 자동 갱신

**검증 에러 메시지**:
| 조건 | 메시지 |
|------|--------|
| ID 형식 오류 | "유효하지 않은 티켓 ID입니다" |
| 존재하지 않는 티켓 | "존재하지 않는 티켓입니다" |

**성공 응답**: 200 OK + 업데이트된 티켓 데이터  
**실패 응답**: 400 Bad Request (형식 오류) / 404 Not Found (존재하지 않는 티켓) + 에러 상세

### FR-006: 티켓 삭제

**설명**: 특정 티켓 ID를 지정하여 해당 티켓을 데이터베이스에서 완전 삭제(Hard Delete)한다.

**API 매핑**: `DELETE /api/tickets/:id`

**입력 필드**: (Path Parameter)
| 필드 | 타입 | 필수 | 제약조건 | 기본값 |
|------|------|------|----------|--------|
| id | number | O | 양의 정수 | - |

**처리 규칙**:
- 요청받은 ID의 티켓이 존재하지 않을 경우 `404 Not Found` 응답
- 존재할 경우 해당 티켓 데이터 레코드를 데이터베이스에서 완전히 삭제
- 삭제 처리 완료 시 200 OK 응답과 성공 메시지 반환

**검증 에러 메시지**:
| 조건 | 메시지 |
|------|--------|
| ID 형식 오류 | "유효하지 않은 티켓 ID입니다" |
| 존재하지 않는 티켓 | "존재하지 않는 티켓입니다" |

**성공 응답**: 200 OK + `{ "message": "티켓이 성공적으로 삭제되었습니다." }`  
**실패 응답**: 400 Bad Request (형식 오류) / 404 Not Found (존재하지 않는 티켓) + 에러 상세

### FR-007: 티켓 상태/순서 변경

**설명**: 칸반 보드에서 드래그 앤 드롭을 통해 특정 티켓의 상태(컬럼)를 변경하거나 동일 컬럼 내에서의 표시 순서(`position`)를 변경한다. 단, 완료(`DONE`) 상태로의 변경은 본 API에서 허용하지 않으며 별도의 티켓 완료 API를 이용한다.

**API 매핑**: `PATCH /api/tickets/reorder`

**입력 필드**: (Request Body)
| 필드 | 타입 | 필수 | 제약조건 | 기본값 |
|------|------|------|----------|--------|
| ticketId | number | O | 양의 정수 | - |
| status | enum | O | BACKLOG, TODO, IN_PROGRESS (`DONE` 불가) | - |
| position | number | O | 실수형 | - |

**처리 규칙**:
- 상태(`status`)와 순서(`position`)를 동시에 업데이트하며, 모든 변경 과정은 **트랜잭션으로 원자성을 보장**함
- 요청받은 `ticketId`의 티켓이 존재하지 않는 경우 `404 Not Found` 응답
- `status`가 `DONE`으로 전달될 경우 `400 Bad Request` 에러 반환 (완료 처리는 별도 API 이용)

**position 재계산 로직**:
- 두 카드 사이에 삽입할 때: `(prev + next) / 2`로 계산
- 카드 사이의 간격이 1 미만일 때: 해당 컬럼 내 전체 티켓을 `1024` 간격으로 일괄 재정렬(Re-indexing)
- 맨 앞에 삽입할 때: 첫 번째 카드의 `position - 1024`
- 맨 뒤에 삽입할 때: 마지막 카드의 `position + 1024`

**비즈니스 로직**:
- `TODO`로 이동 시: `startedAt` = 현재 시각 (`now`)으로 설정
- `TODO`에서 `BACKLOG`로 이동 시: `startedAt` = `null`로 초기화
- 변경된 `status`와 현재 시각, 기존 `dueDate`를 기준으로 `isOverdue` 파생 필드를 재연산하여 반환
- 수정 완료 시 `updatedAt` 필드를 현재 시각으로 자동 갱신

**검증 에러 메시지**:
| 조건 | 메시지 |
|------|--------|
| 잘못된 ticketId 값 | "유효하지 않은 티켓 ID입니다" |
| DONE 상태 요청 | "완료 처리(DONE)는 티켓 완료 기능을 이용해주세요" |
| 잘못된 status 값 | "상태 값은 BACKLOG, TODO, IN_PROGRESS 중 선택해주세요" |
| position 값 누락/오류 | "올바른 위치(position) 값을 입력해주세요" |
| 존재하지 않는 티켓 | "존재하지 않는 티켓입니다" |

**성공 응답**: 200 OK + 변경된 티켓 전체 데이터  
**실패 응답**: 400 Bad Request (입력값/상태 제한 오류) / 404 Not Found (존재하지 않는 티켓) + 에러 상세

### FR-008: Overdue(지연) 판정

**설명**: 종료예정일이 지난 미완료 티켓에 오버듀(지연) 상태를 표시한다.

**API 매핑**: 없음 (조회 시 동적 계산되는 파생 필드)

**판정 규칙**:
- `dueDate < 오늘 AND status ≠ DONE` 일 때 `isOverdue = true`
- DB에 상태를 저장하지 않고, API 조회 응답 시점에 계산하여 전달
- 프론트엔드에서도 동일한 로직으로 클라이언트 사이드 실시간 연산 가능

**처리 방식**:
- `status`가 `DONE`인 티켓은 항상 `isOverdue = false`
- `dueDate`가 없는 티켓은 항상 `isOverdue = false`
- 티켓 조회(`FR-02`), 수정(`FR-04`), 상태/순서 변경(`FR-06`) 응답 데이터 생성 시 해당 규칙 적용
